# 랜딩페이지 만들기

사용자의 아이디어를 **`landing.json` 한 개**로 정리하고, `kit/build.py` 로 **단일 HTML 파일**을 만든다.
CSS·JS가 전부 안에 들어있어서 그 파일 하나만 있으면 열리고 배포된다. npm·빌드도구 필요 없다.

이 키트는 참가자의 프로젝트 폴더 안에 들어간다. `landing.json` 과 결과물은 둘 다 **프로젝트 루트**에 놓인다.

```
내-프로젝트/
├── landing-page-kit/             ← 이 키트
├── landing.json                  ← 내가 만드는 내용 파일
└── 내-프로젝트_landingPage.html   ← 결과물
```

파일 이름의 앞부분은 **프로젝트 폴더 이름**에서 자동으로 가져온다.
다른 이름을 쓰려면 `landing.json` 의 `meta.slug` 를 넣는다 (`slug` → `slug_landingPage.html`).

## 이 키트의 파일

| 파일 | 언제 읽나 |
|---|---|
| `kit/themes.json` | 색상 템플릿 4종. 사용자에게 보여줄 때 |
| `kit/landing.schema.json` | landing.json 을 쓰기 전 (필드 정의) |
| `kit/sections.md` | 목차를 정할 때 (섹션 카탈로그 + 프리셋) |
| `kit/copywriting.md` | 문장을 쓰기 전 |
| `kit/checklist.md` | 빌드 후 점검할 때 |
| `kit/customize.md` | 기본 템플릿에서 더 손볼 때 |
| `kit/build.py` | 빌드 실행 |
| `examples/demo.landing.json` | 형식이 헷갈릴 때 참고 |
| `examples/preview.html` | 결과물이 어떻게 생겼는지 볼 때 |

## 진행 순서

### 1단계 — 프로젝트를 먼저 읽고, 모르는 것만 묻는다

이 키트는 사용자의 **프로젝트 폴더 안에** 들어있다. 질문부터 던지지 말고 **프로젝트를 먼저 훑는다.**

**a. 프로젝트를 스캔한다.** 프로젝트 루트에서 아래를 찾아 읽는다.
- `README.md`, `docs/`, 기획서·발표자료(`.md`, `.txt`, `.pdf`, `.pptx`)
- `package.json` / `pyproject.toml` 의 name·description
- 소스 폴더·주요 파일 이름 (무엇을 만드는 프로젝트인지 드러난다)
- 화면 캡처나 목업 이미지가 있으면 그것도

**b. 아래 5가지를 최대한 채운다.**

| # | 알아야 할 것 | 프로젝트에서 보통 어디에 있나 |
|---|---|---|
| 1 | 서비스/팀 이름 | 폴더 이름, README 제목, package.json name |
| 2 | 누구를 위한 것인가 (구체적인 한 사람) | README 도입부, 기획서 |
| 3 | 그 사람이 겪는 문제 | README "왜 만들었나", 기획서 배경 |
| 4 | 이걸 쓰면 뭐가 달라지나 | README 기능 목록, 소스의 핵심 기능 |
| 5 | 방문자가 할 행동 딱 하나 | 대개 프로젝트에 안 적혀 있다 — 물어봐야 한다 |

**c. 알아낸 것을 먼저 보여주고, 빈칸만 묻는다.**

```
프로젝트를 읽어봤습니다. 이렇게 이해했는데 맞나요?

- 이름: (README에서) 모두의 팀빌딩
- 대상: (기획서에서) 팀을 못 구한 참가자
- 문제: (README에서) 오픈채팅방을 여러 개 뒤져야 함
- 달라지는 점: (소스에서) 스택·시간대 기준 자동 매칭

두 가지만 확인해 주세요.
1. 방문자가 이 페이지에서 할 행동 하나는 뭔가요? (베타 신청 / 다운로드 / 문의 …)
2. 대상을 더 좁힐 수 있나요?
```

**이미 알아낸 것을 다시 묻지 않는다.** 읽은 근거를 괄호로 밝혀서 사용자가 틀린 곳만 바로잡게 한다.
질문은 **한 번에 몰아서** 한다 — 하나씩 주고받으면 대화가 길어진다.

프로젝트가 비어 있어서 읽을 게 없으면 5가지를 그냥 묻는다.

### 2단계 — 색상 템플릿을 고르게 한다 (필수, 건너뛰지 말 것)

`kit/themes.json` 을 읽고 **4가지를 전부 보여준 뒤 고르게 한다.** 임의로 정하지 않는다.
아이템 성격에 맞는 것을 하나 추천하되, 최종 선택은 사용자가 한다.

이렇게 제시한다:

```
1. 미드나이트 블루 — 신뢰·전문성 (B2B, 금융, 클라우드)
2. 웜 샌드         — 따뜻함·사람 중심 (교육, 커뮤니티, 로컬)
3. 포레스트 민트   — 성장·건강 (헬스케어, 친환경, 생산성)
4. 모노 바이올렛   — 모던·첨단 (AI, 개발자 도구, 스타트업)
```

고른 뒤에는 **여기서 더 발전시킬 수 있다는 것도 함께 알려준다.** 4종은 시작점이지 정답이 아니다.

- 색을 비교해 보고 싶으면 `--theme` 으로 파일을 안 고치고 뽑아볼 수 있다
  (`python3 landing-page-kit/kit/build.py landing.json --theme forest -o /tmp/forest.html`)
- 주 색상만 브랜드 색으로 바꾸려면 `themeOverrides`
- 브랜드 가이드가 따로 있으면 `kit/themes.json` 에 테마를 새로 추가
- 모서리·여백·다크모드는 `options`

자세한 방법은 `kit/customize.md`. 사용자가 "이 색만 좀", "좀 더 각지게" 같은 요청을 하면 그 문서를 보고 처리한다.

기본값을 강요하지 않는다. 사용자가 브랜드 색을 이미 가지고 있으면 4종 선택을 건너뛰고
가장 가까운 테마 + `themeOverrides` 로 바로 맞춰준다.

### 3단계 — 목차를 정하고 확인받는다

`kit/sections.md` 의 프리셋 A~D 중 맞는 것을 고른다. 아직 출시 전인 새 서비스라면 보통 **A(제품 소개)** 나 **D(데모·프로토타입)**.

**프리셋은 출발점이다.** 프로젝트에 맞게 섹션을 빼거나 순서를 바꿔서 제안하고,
사용자가 "이건 빼고 저건 넣어줘"라고 하면 그대로 따른다.

**내용을 다 쓰기 전에 목차부터 사용자에게 보여주고 확인을 받는다.** 한 번에 다 만들면 방향이 어긋났을 때 전부 다시 써야 한다.

```
이렇게 구성하려고 합니다:
hero → 문제 → 3단계 동작 → 핵심 기능 → FAQ → 신청 폼 → footer
```

### 4단계 — landing.json 을 작성한다

`kit/landing.schema.json` 의 필드를 따르고, `kit/copywriting.md` 의 규칙대로 문장을 쓴다.
파일은 **프로젝트 루트의 `landing.json`** 으로 만든다 (키트 폴더 안이 아니다).

**절대 지킬 것:**
- **없는 것을 지어내지 않는다.** 후기·도입 기업·실적 숫자가 없으면 그 섹션을 **뺀다**.
  가짜 후기와 가짜 로고는 심사위원이 가장 먼저 알아본다. 빈 섹션을 빼는 게 채우는 것보다 낫다.
  목표치를 쓸 때는 `label` 에 "목표"라고 밝힌다.
- **`[TODO]`, `여기에 내용` 같은 자리표시자를 남기지 않는다.** 모르는 정보는 사용자에게 묻는다.
- **버튼 라벨은 동사+목적어.** "자세히 보기" 금지.
- **주 행동(primary CTA)은 페이지 전체에서 하나로 통일한다.**
- `heading` 은 기능이 아니라 **결과**를 쓴다.

### 5단계 — 빌드하고 점검한다

```bash
# 프로젝트 루트에서 실행
python3 landing-page-kit/kit/build.py landing.json --open
```

빌더가 자체 검사를 돌려서 `[고쳐야 함]` / `[확인 권장]` 을 출력한다.
**`[고쳐야 함]` 이 하나라도 남으면 고치고 다시 빌드한다.**

그다음 `kit/checklist.md` 를 훑는다. 특히:
- 브라우저 폭 375px 에서 가로 스크롤이 안 생기는지
- 다크 모드(우상단 토글)에서 글자가 묻히지 않는지
- 링크가 전부 실제 목적지를 가리키는지

### 6단계 — 사용자에게 넘긴다

프로젝트 루트의 `<프로젝트명>_landingPage.html` 하나가 결과물이다. 배포 방법을 알려준다:
- 더블클릭하면 바로 열린다 (발표할 때는 이걸로 충분하다)
- 웹에 올리려면 그 파일을 빈 폴더에 복사하고 이름을 `index.html` 로 바꾼 뒤
  [netlify.com/drop](https://app.netlify.com/drop) 에 그 폴더를 끌어다 놓는다
- 이미지를 썼다면 이미지 파일도 같이 옮긴다

## 수정 요청이 오면

생성된 HTML 을 직접 고치지 **않는다**. `landing.json` 을 고치고 다시 빌드한다.
직접 고치면 다음 빌드 때 전부 날아간다.

| 요청 | 고칠 곳 |
|---|---|
| "색 바꿔줘" | `theme` 값 교체 |
| "이 색만 살짝" | `themeOverrides.tokens.primary` |
| "모서리 둥글게 / 각지게" | `options.radius` |
| "여백 답답해 / 너무 넓어" | `options.density` |
| "다크모드 빼줘" | `options.darkMode: "light-only"` |
| "이 섹션 빼줘 / 순서 바꿔줘" | `sections` 배열에서 삭제·이동 |
| "문구 바꿔줘" | 해당 섹션의 `heading` / `body` |

`build.py` 가 지원하지 않는 구조를 요구하면(예: 캐러셀, 동영상 배경) 생성된 HTML 을 직접 손봐도 되지만,
**그 경우 사용자에게 "이제부터 landing.json 을 다시 빌드하면 수정이 날아간다"고 반드시 알린다.**

## 흔한 실수

- 색상 템플릿을 안 물어보고 마음대로 정하기 → 2단계는 필수다
- 목차 확인 없이 내용까지 다 써버리기 → 3단계에서 한 번 끊는다
- 후기·로고·숫자를 그럴듯하게 지어내기 → 없으면 섹션을 뺀다
- 빌더 경고를 무시하고 넘기기 → `[고쳐야 함]` 은 반드시 처리한다
